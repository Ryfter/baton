## Key extracted knowledge

**1. The organizing principle is human attention, not tokens.** Kun states it explicitly: "our most precious resource right now, the biggest bottleneck across everything we do with agents is our attention and time." Every design decision in the workflow derives from this: calm mode (a Pi extension that hides all tool calls behind a moving boat so he never watches agents work), voice input ("talking is three times faster than typing," citing a Stanford paper), Lavish artifacts instead of terminal text ("I can never go back to reading text in the terminal"), no-mistakes so he never reviews diffs, `bearings` and `a hoy` as cheap attention-recovery primitives ("just a really good way to catch up... I can just keep spamming a hoy"). His advice on context windows is the purest statement: set one auto-compact constant (500k; he calls Claude Code's 1M default "a little bit too high," sets `CLAUDE_CODE_AUTO_COMPACT_WINDOW=500k`) "and that's all I suggest... otherwise just forget about it... It's okay to not be optimal about everything." He also describes bottleneck migration as the endgame: after firstmate absorbs coordination, "you start to run out of ideas for what to ask it to do. This is a good thing because it indicates the bottleneck is shifting" — from execution → orchestration → attention → ideas/direction.

**2. His actual routing mechanism: agent-authored task-class rules + max-quota-headroom tiebreaker.** The `crew_dispatch.json` file is "not written by hand — I ask first mate to do this. I just tell firstmate what my preferences are and first mate will configure this file for me." Rules map task classes to model *sets*: Fable for new feature work on the paid iOS app ("really good at building good UI... I really want to make sure it's taken good care of"), Codex+GPT for image generation (native tool), a three-model premium set (Fable, Kimi, Astra) for "genuinely very difficult" planning/architecture, a cheap set for "simple bug fix whose root cause and expected behavior is already well defined," Opus+Grok-high as default. When multiple models match a rule, firstmate picks "the one that has the most quota available... so that I don't waste any quota." Note what this is: quota-pool utilization under flat-rate subscriptions, where marginal token cost is zero. Quality within a class is set by hand-curated rules and vibes, not measurement: "don't assume the new model is always better... just use it for a bit and get a sense for how the model behaves" (he prefers Grok 4.5 over 4.6 because 4.6 "has this weird personality where it doesn't quite speak like a human").

**3. The asymmetry: he measures tools rigorously but models not at all.** He benchmarked GitHub MCP vs CLI ("three times more on token cost, and more than double the latency" for identical tasks), measured axi's token-efficient output format ("about 40% tokens compared to using JSON"), and evaluated a 177k-star skill with Program Bench ("5% more tokens while making the results worse... being popular is not the same as actually being good"). This measurement culture applied to tools/skills is exactly the epistemics of a learned router — he just never applies it to model selection. That's the gap Baton occupies.

**4. Hierarchical orchestration with domain-partitioned second mates.** When firstmate saturates — "first mate is like way too busy because it's always orchestrating those tasks and have no time to even talk to me" — he spawns second mates that own domains (ship, wallets, etc.), "every second mate is actually a first mate by itself... it has its own memory and instructions." Placement is capacity-aware: a headless Mac Mini "has more hardware resources than my MacBook... so I assigned a lot of domains to the Mac Mini." All intent funnels through one session: the firstmate session "literally holds all my intent and all the context across every project," summoned from Discord and X via relay bots.

**5. Cost-tiered trust: validation spend is itself governed.** Per-project merge policy lives in `projects.md`: "direct PR plus yolo" for toys ("no one is actually depending on it"), no-mistakes for the rest, YOLO only where changes "will not get released immediately." The explicit heuristic: "for this code change, would you have asked another human to review this code? If you would not have another code reviewer, then you probably don't need no mistakes." And he acknowledges the gate's cost: no-mistakes "takes a long time and uses a lot of tokens. So I don't actually always use no mistakes for every change." The PR's risk assessment (low/medium/high) then routes *his* attention: "when it's low and it's well tested I don't even look at the code."

**6. Standing quality bar via global rules instead of per-PR review.** His 27-line global memory file (kept minimal because "everything in this file gets loaded into the system prompt of every single agent session... it will silently use a lot of our tokens") carries load-bearing rules with stated whys: (a) "when making technical decisions, don't give too much weight to development cost" — because models trained on human data assume human-timescale estimates and "this biases the model to choose cheap solutions that are often low quality, not scalable, or hard to maintain"; (b) bug fixes must start with end-to-end reproduction "as closely aligned with how an end user would experience it as possible" because models default to insufficient unit tests; (c) "be obsessed with pixel perfection... if something clearly looks off, even if it is not directly related... try to get it fixed along the way"; (d) fix lint failures and flaky tests even when not yours. The management philosophy: "Your directors most likely don't review any PRs... they can influence the quality of their team's software by creating good culture and processes."

**7. Memory as cheap accrued lessons — and a warning to fancy memory systems.** Project memory files are "the collective learning of all the agent sessions in this project," grown by correction-and-remember ("every time I saw the agent doing something wrong, I would correct it and ask it to remember"). Skills provide progressive disclosure for conditionally-useful knowledge. His challenge to Grimdex-class tools: "You don't need any fancy memory system to do that. This markdown file is all it takes over time."

**8. Long-running autonomy requires first-class caps.** gnhf exists because harness-native goal loops have a failure mode he experienced: "I might wake up realizing my weekly quota is all [gone]." Token cap, iteration cap, stop condition — set precisely, before bed.

**9. The Token Game: anti-metric-gaming as ideology.** Token maxing is a manufactured incentive structure (circular capital: Microsoft→OpenAI Azure credits recorded as revenue; OpenAI offering "$2 million in every YC company... in the form of token credits"; subsidized $200 subscriptions as a FOMO-generating marketing campaign; enterprises paying "an order of magnitude more expensive" API rates as "the only ones paying the bill"). Key citable stat: Jellyfish's study of 7,000+ engineers found top token spenders produce "roughly twice the output at 10 times the cost." And quotas have a second function beyond cost: "the quota creates an incentive for your power users to also look into how things can be done more efficiently, not just how to spend more tokens." Leaderboards "only reward outliers who typically get there by gaming the metric."

**10. Admitted failure modes of high-throughput orchestration.** He missed the Fly With Me PR ("if you missed it, I did miss it"), the northern-lights prototype was never actually dispatched ("I might have made a mistake in the beginning"), and feedback given directly through Lavish to a crewmate leaves firstmate's decision ledger stale ("first mate thinks it's still open... which is okay"). State leaks between the artifact feedback channel and the orchestrator. Also: the entire environment is Nix-reproduced because "if my AI agent did something stupid and completely destroyed my system, can I recover it instantly" — disaster recovery from agent damage is a first-class requirement.

## Impact on Baton's tech stack

**Router.** The transcripts strongly validate the learned router by showing what its absence costs. Kun maintains his quality taxonomy by hand (task-class rules), calibrates it by vibes ("use it for a bit and get a sense"), and breaks ties on quota headroom rather than quality-per-dollar. His own narration confirms the quota-axi verdict from the prior analysis: the tiebreaker exists because his marginal cost is zero on flat subscriptions and the scarce thing is pool headroom ("so that I don't waste any quota"). Baton's objective must differ structurally: local-fleet capacity is the abundant tier, cloud seats are the quota-capped tiers, so the router maximizes measured quality subject to per-pool headroom — not pool utilization subject to nothing. One refinement the transcripts add: his rules encode quality tiers *per task class* (premium set for hard planning, cheap set for well-defined bugfixes). A learned router should treat his rule file as labeled training data — the taxonomy is already correct in coarse form; learning replaces the vibes-based calibration *within* each class.

**Governor.** gnhf's origin (waking to a burnt weekly quota) is the strongest felt-need evidence for hard caps, and the Token Game gives the Governor a second justification: caps induce efficiency-seeking behavior, not just cost control. Design cue from his context-window advice: the Governor should reduce to one constant per pool (like his 500k auto-compact setting) — set it, then it's invisible. Anything that makes Kevin watch a spend dashboard violates the philosophy below.

**Grimdex / projectmem.** His correction→stored-lesson loop is Grimdex's capture pattern proven at one-person scale, but his "you don't need any fancy memory system" is a direct challenge: Grimdex must earn its complexity through cross-project retrieval and by feeding router features (lessons as routing signals), not through capture. His global-file token-tax insight ("silently use a lot of our tokens") dictates form: lessons should load progressively, skill-style, on relevance — never as always-on prompt weight. His specific rules (anti-dev-cost-bias, repro-first e2e bugfix, fix-adjacent-breakage, pixel-perfect sweeps) are proven seed content for Grimdex/AGENTS.md templates.

**Ringer / no-mistakes.** No-mistakes' pipeline is validated, with a nuance the README can't carry: it is expensive by design and therefore *policy-tiered* per project and per risk. Baton should inherit the PR risk-assessment field as a first-class Governor and router input — high-risk changes get premium review-stage models and mandatory human attention; low-risk ones route cheap and merge on Ringer's exit-0. His evidence pattern (screenshots/video/logs in the PR as "the most direct way to see the change working as you intended") is the output contract Ringer should publish.

**Archon.** Kun uses no DAG engine — his "workflow engine" is an LLM orchestrator whose policy file the LLM itself writes from conversational preferences. Lesson: keep Archon's YAML and the router's policy file as agent-editable artifacts, maintainable by talking ("tell firstmate what my preferences are"). A YAML DSL only Kevin can hand-edit replicates the toil Kun automated away.

**Herdr / firstmate seam.** Fully confirmed in daily use: "Herder is basically my new T-Max," built "in this agent era," with per-harness status lines (model + context %) and cross-machine session management (local vs mini). Baton must not rebuild multiplexing or cross-machine placement. The second-mates pattern (domain-partitioned orchestrators, each with own memory, placed on bigger hardware) is the organizational layer Baton's `baton go` should express, sitting in front of the spawn step as already decided.

**Presidio / local fleet as trust boundary.** His skills-security warning — third-party skills "can instruct your agents to run pretty much anything on your machine... lick your API keys... to untrusted third parties" — plus his local-whisper preference supports the local-first execution/redaction posture and the existing pin-SHAs/vendor-scripts verdict.

**A missing objective term the transcripts expose.** Cheap-model failures cost *captain attention* in re-rolls and bad prototypes — and attention is, by his own argument, the scarcest resource. Baton's learned router should price human touchpoints per task (revisions demanded, escalations, missed-item recoveries — Ringer can proxy these) alongside tokens. A route that saves 90% of tokens but doubles the captain's review iterations is a loss under Kun's own value system.

## What's adoptable piecemeal

1. **One-number context policy**: a single auto-compact threshold per harness as a Baton default; explicitly no context-management UI. His exact numbers: 500k; Claude Code's 1M default is "too high."
2. **Risk-tiered merge policy file** per project (yolo / full-gates) with the "would you ask a human peer to review this?" heuristic as the documented decision rule; wire the resulting risk field into Governor and router.
3. **Captain's-calls ledger** (bearings pattern): a standing skill that snapshots undecided decisions across the fleet and renders them as a decision list with recommendations. Grimdex is the natural host — and hosting it there fixes his Lavish-feedback state-sync bug, because artifact feedback can write back to the ledger.
4. **`a hoy` catch-up command**: cheap summarization of everything the orchestrator said since the captain's last message plus open decisions. Trivial to build, high attention-recovery value.
5. **Agent-authored policy files**: routing rules, merge policies, and Governor budgets written by the agent from conversational preferences, then pinned in-repo.
6. **Global memory seed pack**: his exact rules and rationales (anti-dev-cost-bias, repro-first e2e bugfixes, fix lint/flaky/adjacent-UI breakage unconditionally, no co-author attribution, 27-line global file budget).
7. **Tool-ergonomics bench**: his measurement protocol as a standing Grimdex bench — same-task CLI-vs-MCP comparisons, token-format A/B (~40%), skill evals with a publish-or-don't-install bar (Program Bench's +5%-tokens-worse result as the cautionary tale). Feed results into router features.
8. **Calm mode**: suppress tool-call spam behind a liveness indicator with a toggle. Cheap `baton go` UX adoption.
9. **Voice-first input** with local whisper and a vocabulary system prompt (project names) — directly transferable.
10. **First-class loop caps**: token/iteration/stop-condition on every long-running Archon workflow, Governor-enforced (gnhf pattern).
11. **Anti-gaming reporting rule**: never present token counts as success anywhere in Baton's outputs; report quality-per-dollar and outcome hooks. The Jellyfish 2x-output/10x-cost stat is the citable justification.
12. **Nix-style reproducibility with pinned inputs**, framed as disaster recovery from agent damage — consistent with the existing pin-SHAs verdict on firstmate.

## The core tension

Kevin's summary — "he just looks at models with the least token usage" — is slightly off in a way that matters. Kun's tiebreaker is *max quota headroom* under flat-rate subscriptions, not least tokens; and in the Token Game video he argues explicitly that "token usage is not even a productivity metric." But functionally Kevin's instinct is right: both are non-quality metrics. Kun's system never measures model quality per task — it hand-codes coarse quality classes, breaks ties on pool economics, and lets human taste at the artifact-review layer catch the misses. Baton's learned quality-per-dollar router is the industrialization of the thing Kun currently does by vibes and rules-of-thumb. The transcripts validate this repeatedly: his tool benchmarks prove measured-beats-reputation (MCP 3x, skills +5%-worse); his own model advice ("don't assume the new model is better, just use it and get a sense") is manual, unsystematic calibration; his dispatch rules are a hand-maintained draft of the taxonomy a router learns.

The deeper tension is philosophical, and it cuts at Baton. Kun's entire system is built on demoting cost-optimization as a *human* activity: "it's okay to not be optimal about everything," "don't give too much weight to development cost," quota management delegated to the agent, caps reduced to one forgotten constant. His reconciliation of his own apparent contradiction — he preaches anti-optimization yet built quota-axi, axi's 40% token savings, and skill benchmarks — is a clean line: **all spend optimization lives below the captain's attention line; anything that requires ongoing human attention to save tokens is itself the bug.** That is the design law Baton must adopt or its differentiator becomes its liability. A learned router that surfaces dashboards, score calibrations, and threshold fiddling to Kevin would repeat exactly the mistake Kun warns about — "if your brain is thinking about the context window all the time, you don't have enough time to think about what to build."

Where "cheapest adequate model" helps: the 80% of well-defined work (his "simple bug fix" class) where no-mistakes/Ringer gates catch failures anyway — his own rules route this class cheap, and measured routing does it better. Where it actively hurts, and the transcripts say so in his words: (1) design and planning — his anti-dev-cost-bias rule exists precisely because cost-pressure corrupts architecture choices toward "cheap solutions that are often low quality, not scalable, or hard to maintain"; Baton must encode this as charter: the router optimizes execution economics, and cost logic never touches design-space decisions. (2) Flagship/taste-laden surfaces — he pays premium (Fable on the paid iOS app) for qualities he can articulate but not benchmark; a router can beat this intuition only if it measures the right thing, which means pricing human re-roll attention, not just tokens. (3) Adopting quota-axi's ranking as-is routes as if local GPUs don't exist — his narration explains why: he has zero local inference, so pool-headroom maximization is rational *for him* and wrong as a general objective.

The resolution for Baton: the bottleneck-migration frame. Kun's real success metric isn't token efficiency — it's that his bottleneck keeps moving up (execution → orchestration → attention → ideas; "you start to run out of ideas... the bottleneck is shifting"). Baton's Governor-plus-learned-router should be evaluated the same way: does it keep Kevin's bottleneck at "what should we build," with all spend/quality optimization autonomous, cap-bounded, and invisible except as captain's calls, risk flags, and evidence-backed PRs? Token-per-quality is the instrument; attention-per-shipped-outcome is the objective. Kun's system is the strongest existing proof that the second metric is the one that compounds.
